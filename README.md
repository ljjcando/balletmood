# Ballet Mood

> 记录每一次优雅的进步

一款专为芭蕾舞者设计的微信小程序，采用莫兰迪燕麦色系，帮助舞者记录每日练习感悟、课程进展，追踪芭蕾术语学习。

---

## 核心功能

### 1. 日历记录
- 月视图日历，直观查看练习记录
- 点击已有记录进入**展示模式**（明信片卡片）
- 点击空白日期进入**编辑模式**（新建记录）
- 有记录的日期显示特殊标记，有图片的日期显示缩略图

### 2. 术语标签
- 内置常用芭蕾术语（Rond de jambe、Adagio、jete 等）
- 支持多选术语标签
- 支持添加自定义术语
- 长按术语可删除

### 3. 多课程展示
- 单日可记录多节课程
- 支持选择课程类型（入门、初级、中级、PBT 等）
- 记录每节课的时长
- 详情页展示所有课程标签，横向排列自动换行

### 4. 图片上传
- 支持从相册或拍照上传练习照片
- 自动裁剪为 3:4 竖向比例
- 详情页有图时显示大图，无图时隐藏图片区域

### 5. 数据统计
- 本月目标设定
- 本地存储，数据永久保存
- 支持编辑和删除历史记录

### 6. 身体部位标记
- 标记练习涉及的身体部位（核心、脚背、外开、背部、手臂）
- 多选胶囊标签形式

## 特别记录：本次优化重点 (v1.1.0)

### 1. 展示模式与编辑模式的分离
**问题**：原逻辑中，点击有图片的记录进入展示模式，无图片记录直接跳转编辑模式。

**优化**：
```javascript
// 统一入口逻辑：只要已有记录，均进入展示模式
if (record) {
  this.openPostcard(date);   // 展示模式
} else {
  this.openEditModal(date);   // 新建模式
}
```

**效果**：用户体验更连贯，可先查看再决定是否编辑。只有点击"重新编辑"按钮才进入编辑态。

## 数据结构

### 单条记录格式
```javascript
{
  photo: "cloud://...",         // 图片路径（可选，云端 fileID；旧版本可能残留本地临时路径）
  note: "今天的练习感悟...",     // 文字记录
  terms: ["Adagio", "jete"],   // 术语数组
  bodyParts: ["核心 Core"],     // 身体部位数组
  courses: [                    // 课程数组
    { name: "初级", duration: "1.5" },
    { name: "PBT", duration: "1.0" }
  ],
  updatedAt: "2025-03-21T..."
}
```

### 图片兼容说明
- 1.0.4 及后续版本会优先将图片上传到云端，并在记录中保存 `cloud://...` 文件 ID。
- 旧版本 1.0.2 及更早版本，部分记录里可能仍是手机本地临时路径。
- 当这些旧路径失效时，记录本身仍会保留，界面会提示：`图片已过期，请重新上传`。

## 技术栈
- 微信小程序原生框架
- 本地存储 (`wx.setStorageSync`)
- 微信云开发数据库（CloudBase）
- 微信云存储（图片 `cloud://...` fileID）

## 当前数据策略（v1.0.9 候选版）

- 当前设备以本地数据为准，云端只用于备份和同一微信账号换机恢复。
- 新增、编辑后先写本地，再后台备份对应记录到云端。
- 删除后本地立即消失，并把云端删除写入持久待办；失败时下次启动继续重试。
- 替换、清空照片或删除整条记录后，会清理对应的旧云文件；清理失败时下次启动继续重试。
- 只有新设备首次打开且本地尚未初始化时，才从云端恢复当前微信账号的记录和个人配置；即使只有月度目标、没有日记，也能恢复。
- 从旧版本升级时，会识别既有本地记录存储键；即使记录已删空，也不会误当成新设备恢复云端旧记录。
- 不支持多台设备之间的实时或自动同步；启动、进入前台和下拉刷新都不会用云端数据覆盖本地。

## 云开发索引配置

当前版本已经使用结构化云同步，涉及 3 个集合：

- `ballet_mood_records`
- `ballet_mood_profiles`
- `ballet_mood_users`（旧版兼容用 legacy 集合）

这些索引不是仓库里的代码文件，必须在微信开发者工具或云开发控制台里手动创建。

### 推荐索引

#### 1. `ballet_mood_records`

用途：按当前用户读取全部日记记录，是最重要的一组索引。

建议创建：

- 组合索引：`_openid` 升序，`dateKey` 升序
- 组合索引：`_openid` 升序，`updatedAt` 降序

说明：

- `_openid + dateKey` 适合按用户维度维护每天唯一记录，也方便后续按日期做精确查找。
- `_openid + updatedAt` 适合按用户读取最近更新的记录，后续如果做“最近编辑”“增量同步”会更稳。

#### 2. `ballet_mood_profiles`

用途：按当前用户读取术语、目标、课程标签等个人配置。

建议创建：

- 组合索引：`_openid` 升序，`updatedAt` 降序

说明：

- 当前代码会按 `_openid` 读取当前用户 profile，并在多条记录并存时优先挑最新一条。

#### 3. `ballet_mood_users`

用途：兼容旧版本单文档快照恢复。

建议创建：

- 组合索引：`_openid` 升序，`updatedAt` 降序

说明：

- `_openid + updatedAt` 用于优先查当前用户的最新 legacy 快照。
- 不允许在当前用户 `_openid` 查询为空时退回全库文档，避免跨用户恢复数据。

### 创建步骤

1. 打开微信开发者工具。
2. 进入“云开发”面板。
3. 打开对应环境。
4. 进入“数据库”。
5. 选择集合，例如 `ballet_mood_records`。
6. 打开“索引”页签。
7. 按上面的字段顺序创建索引。
8. 等索引状态变成“可用”后，再创建下一条。

### 最小必建集合

如果你这次只想先补最关键的，优先级是：

1. `ballet_mood_records`: `_openid` + `dateKey`
2. `ballet_mood_profiles`: `_openid` + `updatedAt`
3. `ballet_mood_users`: `_openid` + `updatedAt`

先把这 3 条建上，当前版本的本地备份、云端删除和换机恢复流程就够用了。

- 修复修改本月目标后另一台设备无法识别变化的问题：profile schema 给 goal 加上 `goalUpdatedAt` 时间戳（与 terms / courseTags 一视同仁），freshness 比较时能识别 goal 的独立变更
- 修复删除记录后 2-3 秒被云端"复活"、跨设备/重启同步失败的问题：新增 `deleteSingleRecordInCloud` 精准删除函数（按 dateKey 把云端所有匹配文档批量标记 isDeleted=true），删除流程改走轻量可靠路径，不再依赖原有长链路
- 大幅提升电脑端启动同步速度：从"先做完整同步再显示最新"改为"先快速拉云端 apply、后台再做兜底 push"，跨设备场景下用户几秒内就能看到另一台设备的最新更新，不再需要等 30-60 秒（云端历史脏文档多时尤其明显）
- 顶部新增手动"刷新"按钮：PC 版微信不支持下拉刷新手势，加了一个 🩰 芭蕾舞鞋图标在头部右上角，点一下就能主动拉云端最新数据（配合旋转动画和"已刷新"toast 反馈）；跟项目品牌一致（README 的 "Made with 🩰 for ballet dancers" 就是它）；手机端下拉刷新继续可用，此按钮作为补充

#### 本次解决的 Bug / 逻辑问题
- 移除 `pickNewerRecord` 中的 photo 兜底逻辑：当新版本 photo 为空、老版本 photo 有值时，旧逻辑会用老照片覆盖新版本的空值
- 该兜底原本是为了 v1.0.4 之前"云端 photo 字段意外为空覆盖本地有效照片"的场景准备，已通过 v1.0.4 的"先上传 cloud:// fileID 再写入 record"流程从根本上解决
- 当前架构下，唯一会触发这段兜底的场景反而是用户主动删除照片，导致删除无效
- 修复照片右上角 × 同时绑定 `bindtap` 与 `catchtap` 导致事件冒泡，点击 × 同时触发删除与"打开相册"弹窗的问题
- 修复 `photo-helper.js` 中 `editImage` 的 fail 回调误把原图当作成功选择的问题，使裁剪界面点"取消"真正取消照片选择
- 修复 `index.wxml` 中 `photo-upload-mini` 外层绑定 `bindtap` 导致有照片时点照片本身也会弹出选图框的问题，将选图入口下放到"添加照片"占位与"图片已过期"提示两个内层分支
- 修复 `photo-helper.js` 的 fail 回调一刀切静默后，导致 PC 端等不支持 `wx.editImage` 的平台选图后无反应的回归问题：改为按 `errMsg` 区分用户取消与平台不支持，后者回退使用原图
- 优化 `saveRecord` 的保存反馈：从"等待 `await pushSnapshotToCloud` 串行完成后再提示成功"，改为本地保存后立即提示成功、云端同步由 `syncCurrentSnapshotInBackground` 后台进行，与项目其他写入流程的设计保持一致
- 新增 `saveSingleRecordToCloud` 精准同步函数，单条记录的保存改走轻量路径，不再调用 `fetchStructuredCloudSnapshot` 拉全量、也不再 `saveRecordSnapshot` 重写所有记录；启动/术语/目标/课程标签/删除等其他场景继续走原有全量同步以保证数据完整性
- 修复 `fetchLatestCloudSnapshot` 在返回前提前调用 `stripDeletedSnapshot` 把已删除项擦掉，导致上层 `shouldApplyCloudSnapshot` 通过 freshness 比较时看不到删除事件时间戳的问题；改为返回完整 snapshot，由 `applySnapshotToPageAndRender` 在展示前 strip，并在云端来源时同步写回本地缓存
- 修复本月目标缺少独立 `goalUpdatedAt` 字段，导致 `mergeSnapshots` 用 `||` 短路合并、`getSnapshotFreshness` 比较时也看不到 goal 变化的问题；与 terms / courseTags 一致地引入 `goalUpdatedAt` 时间戳，写本地存储、写云端 profile、读云端 profile、`buildCurrentSnapshot`、`getSnapshotFreshness` 全链路同步处理
- `saveGoal` 增加幂等检查（值未变则跳过 setData/同步/toast）和成功反馈（"目标已更新" toast），并把 goal 升级为时间戳驱动的可识别变更
- 删除流程从全量同步链路（`syncCurrentSnapshotInBackground` + `deletedRecordDates` + `replaceRecords`）改走精准路径：新增 `deleteSingleRecordInCloud(dateKey)` 按 dateKey 拉云端所有匹配文档（支持分页）后批量 update 为 `isDeleted=true`，并新增 `syncSingleRecordDeleteInBackground` 在后台触发；`deleteRecord` 和 `deleteFromPostcard` 都改用新路径，避免原链路上 update 被静默吞错导致云端 isDeleted 一直停在 false 的问题，同时顺手处理历史"重复 add"累积的多份脏文档
- 修复 `loadStorageData` 里 `hasLocalRecords` 分支的启动同步顺序问题：原逻辑是本地渲染后同步等待 `migrateLocalSnapshotToCloud` 全量同步完成（内部要拉云端所有历史 records、合并、逐条 update 回云端），云端有大量脏文档时会阻塞 30-60 秒，跨设备最新数据迟迟看不到；改为先调用 `fetchLatestCloudSnapshot` 快速拉云端最新快照 apply 到页面（几秒内看见），随后再后台跑 `migrateLocalSnapshotToCloud` 作为兜底 push（失败不影响页面显示，本地可能未同步的更新仍能被后台推到云端）

#### 修复总结
- 数据层：移除 `pickNewerRecord` 中的 photo 兜底，主动删除照片在所有保存/同步场景下都能生效
- 交互层：照片删除增加确认对话框、裁剪界面点取消真正取消选择，避免误操作与"取消却被保存"的体验问题
- 拍照分支行为不变；其他保存、合并、同步、跨设备读取流程不受影响
- 体验版已验证：删除图片+保存后图片不再回到日历，裁剪界面点取消不再误保存原图

- 此前因兜底逻辑导致"删除照片无效"的用户，升级后再次点击删除即可正常生效
- 照片删除新增二次确认，原"误触删除"场景下用户可以取消保留照片

- 修复刷新与重新进入小程序仍无法拉回完整云端记录的问题
- 修复保存流程因云端读取不全，将"已存在的记录"误判为"不存在"而重复写入云端，导致同一日期在云端积累多条文档的问题

#### 修复总结
- 本次只动了一个核心读取函数 `listCurrentUserRecordDocs`，因其是云端记录读取的唯一入口，所有依赖它的同步、保存、刷新流程都跟随修好
- 客户端读取时已经具备同日期多文档去重逻辑，故云端历史遗留的重复文档不会影响功能展示，可保留观察
- 真机已验证：电脑端记录 27 条后，手机端刷新可完整拉回全部 27 条记录

#### 发版备注
- 受影响最重的是云端记录超过 20 条的重度用户；升级新版本后，其完整历史会在下次打开小程序时自动从云端恢复
- 云端历史可能积累的重复文档暂未清理，不影响读取与展示；如需清理可在后续版本中通过云函数批量处理

### v1.0.4 发布记录 (2026-04-11)

#### 本次更新内容

- 云开发数据库已补充本轮需要的关键索引，降低按用户查记录与恢复历史时的扫描成本

#### 本次解决的 Bug / 逻辑问题
- 修复微信小程序缓存清理后，历史记录无法稳定从云端恢复的问题
- 修复同一天存在多条云记录时，可能拿到较差版本记录的问题
- 修复云端较新的记录照片为空时，把本地有效照片覆盖掉的问题
- 修复保存后云端返回新的 `cloud://...` 图片 ID，但页面仍保留旧本地路径的问题

- 修复课程标签可能重复保存、重复展示的问题

#### 修复总结
- 这一轮重点不在新功能，而在“记录链路闭环”。
- 现在一条记录从新建、编辑、删除，到本地保存、云端同步、启动恢复，链路已经统一。
- 图片处理也从“依赖本地临时路径”改成了“优先持久化 + 云端 fileID”，降低了后续丢图概率。
- 对旧数据保留兼容逻辑，已经存过的历史记录不会因为版本升级直接失效。

- 若旧记录中的图片来自更早版本，首次打开时仍可能出现“图片已过期，请重新上传”的提示；这是旧临时路径失效后的兼容兜底，不影响文字记录本身。
